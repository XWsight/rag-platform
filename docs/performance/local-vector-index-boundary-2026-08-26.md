# 本地精确向量索引：规模边界记录（2026-08-26）

## 结论

当前 `LocalVectorIndex` 使用进程内精确余弦扫描。它在小型知识库上有明确、
可复现且无需网络数据库的行为，但查询延迟随 chunk 数线性增加。在本次受控
微基准中，5,000 个 384 维向量的 P95 为 **125.693 ms**；这尚未包含 Embedding、
BM25、融合、重排序、网络或并发。因此把它作为交互式端到端服务的长期默认后端
缺乏性能余量。

本记录支持后续通过既有 `IndexRepository` / `VectorIndex` 端口评估可选 ANN
适配器；它**不**证明 ANN 一定更快、更准确或更适合当前部署，替换前仍须完成
召回、持久化、迁移/回滚和安全边界测试。

## 命令

```bash
python3 scripts/benchmark_local_index.py \
  --sizes 100,1000,5000 \
  --dimension 384 \
  --queries 30 \
  --warmup 5 \
  --require-clean \
  --top-k 5
```

该脚本构造确定性非零向量，只执行 `LocalVectorIndex.search`。它排除了：文档
解析、Embedding 生成/模型冷启动、JSON 持久化、BM25、RRF、重排序、网络、
多租户和并发。因此下列数值只能用于评估精确扫描本身，不能当作 API SLA 或
端到端检索延迟。

当前脚本的 JSON schema 为 v3；新运行会自动写入参数、Python/平台、可见 CPU 数、源码提交和
工作区是否干净。将来更新本记录时，应保留原始 JSON、在比较前核对这些环境字段，并以 `--require-clean`
生成可用于正式比较的报告。

## 下一步判定

1. 若目标知识库通常低于约 1,000 chunks，保留当前精确后端；它简单、可审计，
   且本次微基准仍留有一定检索预算。
2. 若常态接近或超过 5,000 chunks，先在真实文档和 Embedding 已预热条件下测量
   端到端 P50/P95，再评估 ANN 适配器。不能只凭本微基准直接更换后端。
3. 任何候选后端必须保持现有索引 ID、租户边界、持久化校验和显式删除语义；
   同时在冻结 retrieval suite 上不得降低 Recall@k、MRR@k、nDCG@k 或关键安全
   路由切片。
